## 📊 资源感知调度器处理逻辑详解

### **总体处理流程**

```
┌──────────────────────────────────────┐
│  scheduleLoop() 定时调度主循环 (5s)   │
└────────────────┬─────────────────────┘
                 │
        ┌────────▼────────┐
        │ 尝试获取Leader  │ (分布式锁选举)
        │ 身份获取失败    │
        │ 则跳过本轮      │
        └────────┬────────┘
                 │ Leader
        ┌────────▼──────────────────┐
        │ 扫描PENDING任务并计算     │
        │ 综合优先级                │
        │ (优先级+等待时长的组合)   │
        └────────┬──────────────────┘
                 │
        ┌────────▼──────────────────┐
        │ 对每个任务执行调度        │
        │ 单任务处理流程            │
        └────────┬──────────────────┘
                 │
    ┌────────────┴────────────┐
    │ 对单个任务的处理        │
    │                         │
    ├─ 获取任务分布式锁      │
    ├─ 二次拉库检查PENDING    │
    ├─ 检查租户配额           │
    ├─ 获取所有在线节点       │
    ├─ Best Fit选点           │
    │  └─ canFit硬约束检查    │
    │  └─ 计算匹配分          │
    │     (资源浪费率+负载+类型)│
    ├─ 预留资源               │
    ├─ 乐观锁更新任务状态     │
    ├─ 提交执行器             │
    └─ 失败则回滚             │
```

### **核心处理阶段**

#### **第1阶段：Leader选举**
- 使用Redis分布式锁，所有调度器实例竞争
- 获得锁的实例成为Leader，获得30秒的领导权
- 失败则自动退出本轮调度

#### **第2阶段：任务扫描与优先级排序**
计算综合优先级 = 基础优先级 × 权重 + 等待时长 × 老化权重

```
公式：优先级分 = 10.0 × (priority/10) + 0.1 × (等待时长秒数/3600)
效果：优先级高的任务优先，等待越久的任务权重越高
```

#### **第3阶段：单任务调度处理**
分三层检查：
1. **任务级检查**：分布式锁 → 任务状态 → 租户配额
2. **节点级检查**：获取在线节点 → 硬约束检查(canFit)
3. **分配级检查**：资源预留 → 状态流转 → 执行器提交

#### **第4阶段：Best Fit选点**
计算节点综合匹配分：
- **资源浪费率** (50%权重)：选择浪费最少的节点
- **负载因子** (30%权重)：优先选择可用资源多的节点  
- **类型匹配** (20%权重)：CPU任务选CPU节点，GPU任务选GPU节点

综合分数 = (1 - 浪费率) × 0.5 + 负载因子 × 0.3 + 类型匹配 × 0.2

#### **第5阶段：资源分配与事务性提交**
- 预留资源（占用配额）
- 乐观锁更新任务状态PENDING→RUNNING
- 绑定节点ID
- 失败则自动回滚资源预留

|----|------|------|--------|------|
| **核心入口** |
| 1 | `scheduleLoop()` | 无 | void | 调度主循环，由@Scheduled定时触发(每5s)，是整个调度引擎的心脏 |
| **任务扫描与优先级** |

| 3 | `buildWithPriorityFromOrderedIds(List<Long> ids)` | ids | `List<TaskWithPriority>` | 根据已排序的ID列表构建任务优先级对象，计算等待时长 |

| **任务调度流程** |
| 5 | `scheduleTask(TaskInstance taskInstance)` | 任务实例 | boolean | 单任务调度入口，包含分布式锁、配额检查、Best Fit选点等完整逻辑 |
| 6 | `scheduleTask(TaskInstance, ResourceNode)` | 任务、指定节点 | boolean | 调度任务到指定节点（内部方法），跳过Best Fit直接分配 |

| 8 | `checkQuota(TaskInstance task)` | 任务 | boolean | 检查租户配额是否充足，基于CPU/内存/GPU维度 |

| **Best Fit选点系列** |
| 10 | `listOnlineNodes()` | 无 | `List<ResourceNode>` | 查询所有ONLINE状态的资源节点 |

| 12 | `calculateFitScore(ResourceNode, TaskInstance)` | 节点、任务 | double | 计算节点与任务的综合匹配分(资源浪费率+负载+类型匹配) |
| 13 | `calculateTypeMatch(ResourceNode, ResourceRequirement)` | 节点、需求 | double | 计算节点类型与任务的异构匹配度(CPU/GPU/MIXED) |
| **资源预留与回滚** |
| 14 | `reserveResource(TaskInstance, ResourceNode)` | 任务、节点 | Long | 调用资源服务预留资源，返回预留使用ID |
| 15 | `rollbackReservation(TaskInstance, Long usageId)` | 任务、使用ID | void | 释放已预留的资源（失败时调用） |
| 16 | `rollbackAfterDispatchFailure(TaskInstance, Long)` | 任务、使用ID | void | 分发失败后的完整回滚（状态复原+资源释放） |
| **需求解析与工具** |
| 17 | `parseRequirement(String requirementJson)` | JSON字符串 | `ResourceRequirement` | 解析任务resourceRequirement字段，转换为对象并验证字段合法性 |
| 18 | `hardConstraintNodeType(ResourceNode, ResourceRequirement)` | 节点、需求 | boolean | 验证节点类型是否满足任务硬性类型约束 |
| 19 | `parseNodeTypeFromString(String raw)` | 字符串 | `NodeType` | 字符串转NodeType枚举(CPU/GPU/MIXED)，容错处理 |

## 🔑 关键设计要点

### **1. 多维度优先级排序**
```
基础优先级 (业务优先级) + 老化权重 (等待时长)
= 新用户任务有机会，等待的任务也有救赎机制
```

### **2. Best Fit算法三维评分**
```
综合分 = (1 - 资源浪费率) × 0.5      // 最小浪费
       + 节点负载因子 × 0.3          // 负载均衡
       + 类型匹配度 × 0.2             // 异构适配
       
效果：同时优化资源利用率、负载均衡、异构感知
```

### **3. 事务性处理确保一致性**
```
预留资源 → 乐观锁更新 → 执行提交
失败即回滚，无中间态暴露
```

### **4. 分布式锁保证单点处理**
```
不同调度器实例竞争同一个Leader身份
同一任务不会被多个实例并发调度
```

### **5. 硬约束 vs 软分优化**
```
canFit()    → 硬性约束（必须满足，否则无法运行）
calculateFitScore() → 软性评分（在满足硬约束基础上优化）
```

---

这个设计实现了一个**分布式、多维优化、异构感知**的调度器，适合生产环境的复杂资源调度场景。
